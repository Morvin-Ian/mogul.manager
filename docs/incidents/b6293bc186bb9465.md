# Database connection refused on port 5432 — PostgreSQL unavailable at startup

## What happened

The application's API server tried to connect to PostgreSQL on port 5432 but the connection was refused. This means the database server was either not yet running, not listening on that port, or was unreachable from the API container. A follow-up `CRITICAL` log 5 minutes later confirms the database never became reachable within the standard timeout window, rendering the entire application inoperable.

## Root cause

The error originates from **`database.py` (line 6)**, where SQLAlchemy's `create_async_engine` is called with the connection string loaded from `settings.database_url`:

```python
engine = create_async_engine(settings.database_url)
```

The `database_url` is configured (per **`.env.example` lines 1–2** and **`docker-compose.yml` line 15**) as:

```
postgresql+psycopg://${POSTGRES_USER}:${POSTGRES_PASSWORD}@db:5432/${POSTGRES_DB}
```

The host `db` resolves to the `db` Docker service defined in **`docker-compose.yml` lines 40–53**. Internally, PostgreSQL listens on port 5432 (mapped to host port 5433).

The root cause is a **startup race condition** in **`docker-compose.yml` line 16–18**:

```yaml
depends_on:
  db:
    condition: service_started
```

`service_started` only guarantees that the PostgreSQL **container** has started — **not** that the PostgreSQL **process** inside it is ready to accept TCP connections. PostgreSQL can take 10–30 seconds to initialize its data directory, replay WAL, or recover after a restart, especially on first deployment.

The startup script **`docker/local/api/start`** (line 4) runs `alembic upgrade head` immediately, which needs a live database connection and will fail with "Connection refused" if PostgreSQL isn't ready yet. The API's own `lifespan` handler in **`main.py` lines 104–125** and every route handler (e.g., `routes/dependencies.py` lines 46–47 using `Depends(get_db)`) all depend on the same database session factory from `database.py`, so the entire application is blocked.

## Suggested fix

### Fix 1: Add a healthcheck to the `db` service and switch to `condition: service_healthy`

**File: `docker-compose.yml`** — Add a healthcheck to the `db` service and update the `api` dependency condition:

```yaml
services:
  db:
    image: pgvector/pgvector:pg17
    container_name: mogul-db
    restart: unless-stopped
    ports:
      - "5433:5432"
    environment:
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: ${POSTGRES_DB}
    volumes:
      - pgdata:/var/lib/postgresql/data
    networks:
      - mogul-net
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER} -d ${POSTGRES_DB}"]
      interval: 5s
      timeout: 5s
      retries: 10
      start_period: 30s

  api:
    # ... existing config ...
    depends_on:
      db:
        condition: service_healthy    # ← was: service_started
```

The `pg_isready` utility is built into the PostgreSQL image and returns 0 when the server is accepting connections.

### Fix 2 (belt-and-suspenders): Add a wait-for-it script to the API startup

**File: `docker/local/api/start`** — Wrap the startup with a retry loop so transient failures during deployment don't crash the container:

```sh
#!/bin/sh
set -e

echo "Waiting for database..."
for i in $(seq 1 30); do
  pg_isready -h db -p 5432 -U "${POSTGRES_USER}" -d "${POSTGRES_DB}" && break
  echo "Database not ready — attempt $i/30"
  sleep 2
done

uv run alembic upgrade head

exec uv run fastapi dev main.py --host 0.0.0.0 --port 8000
```

(Requires `postgresql-client` to be installed in the API Docker image, or alternatively a Python-based retry loop using the existing `psycopg` dependency.)

### Fix 3 (optional): Add connection-retry logic in `database.py`

**File: `database.py`** — Use SQLAlchemy's `pool_pre_ping` and a retry-capable engine creator so transient failures at any point (not just startup) are handled gracefully:

```python
engine = create_async_engine(
    settings.database_url,
    pool_pre_ping=True,          # verify connections before handing them out
    pool_size=5,
    max_overflow=10,
)
```

This won't fix the initial startup problem on its own, but it prevents cascading failures if the database is briefly restarted while the API is already running.
